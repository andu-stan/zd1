# Our forks of upstream crates

The module's receivers build on upstream Rust crates changed for this CPU and kernel. The changes live on the
`zeppelin` branch of a fork on GitHub, one commit per change (each one meant as an upstream pull request); the apps
pin them by commit, once, in the top `Cargo.toml` (shairplay in `[workspace.dependencies]`, librespot and libmdns in
`[patch.crates-io]`).

| Fork (branch `zeppelin`) | Upstream | Base | Used by |
|---|---|---|---|
| https://github.com/pawlowskialex/shairplay-rust | https://github.com/metaneutrons/shairplay-rust (LGPL-3.0-or-later) | 2fb72b3 (0.10.0) | `zd1-airplay`: AirPlay 1/2 |
| https://github.com/pawlowskialex/librespot | https://github.com/librespot-org/librespot (MIT) | `dev` | `zd1-spotify`: every librespot crate comes from the fork, four of them changed |
| https://github.com/pawlowskialex/libmdns | https://github.com/librespot-org/libmdns (MIT) | v0.10.1 | Spotify discovery |

To change one: clone the fork, work on `zeppelin` (a commit per change, rebased onto upstream when it moves; the
committer and author email the GitHub noreply address, or the push is refused), push,
and move the pin (`rev` in the top `Cargo.toml`; the next build updates `Cargo.lock`). To try a change before
pushing it, point the workspace at the checkout in a Cargo config that isn't committed, passed with `--config`:
`[patch."https://github.com/pawlowskialex/shairplay-rust"] shairplay = { path = "/path/to/checkout" }`.

## Our changes to librespot and libmdns
For zd1-spotify (`module/os/apps/zd1-spotify`, `docs/streaming.md`); each keeps upstream's behaviour by default,
and all of it is meant for upstream. On librespot's `zeppelin` our commits come first (each applies to `dev`, or to
the one it builds on), then two upstream PRs as their authors wrote them, then the commit that needs the second.

| Change | Why (on the module) | Files |
|---|---|---|
| playback: `decoder::DecoderPlugin` (`PlayerConfig::decoder_plugin`): the application's decoder, tried before the built-in ones, with the format choice steered to what it takes; it gets the decrypted file (`ReadSeek`) after Spotify's own Ogg header | Vorbis through our fixed-point decoder on Warp0 or the ARM: Symphonia's float Vorbis costs ~100 % of a soft-float ARM926 | `src/decoder/mod.rs`, `src/config.rs`, `src/player.rs` |
| playback: `AudioPacket::S16`: integer samples from a decoder; the player applies volume and the basic normalisation to them as a Q16 gain, the byte sinks pass them through (other formats via the f64 path), the other backends read them through `AudioPacket::f64_samples` | f64 samples would cost the soft-float CPU several % in conversions and multiplies alone | `src/decoder/mod.rs`, `src/player.rs`, `src/audio_backend/mod.rs` |
| playback: feature `symphonia` (default on, also in the `librespot` crate): off, no built-in decoders and no local files | 350 KB less in the system image | `Cargo.toml`, `src/lib.rs`, `src/local_file_none.rs`, `src/player.rs`, `src/decoder/mod.rs` |
| audio: `AudioFetchParams::memory_limit: Option<usize>` (`None`, the default: the temporary file as upstream): at most that much of the file in memory, 32 KB blocks, those farthest behind the reader dropped first and removed from the downloaded and requested sets (a seek back downloads them again), prefetch only as far as the window reaches; the cache gets the file when it was all there | upstream keeps every track whole in a temporary file: here /tmp is RAM, 4-12 MB a track, twice around a track change, in 28 MB of RAM | `src/fetch/store.rs` (new, + tests), `src/fetch/mod.rs`, `src/fetch/receive.rs` |
| playback: a refused audio key (`AudioKeyError::AesKey`) stops the player on the track and sends `PlayerEvent::AudioKeyUnavailable` instead of `Unavailable`: librespot-org/librespot#1799 (Carmine Paolino, Kristoffer Haugland), its commit as is | the account's keys are refused for every track: the player skipped through the whole queue in seconds [HW 2026-10-28] | `src/player.rs`, `src/player_event_handler.rs` |
| connect, four commits: a skip that fails (context not resolved yet) stops on the current track instead of returning with the state left loading; five unavailable tracks in a row stop playback; play and play/pause while stopped load the current track again; `AudioKeyUnavailable` leaves the device stopped on its track (on #1799) | the speaker sat "buffering" in the app after a failed track, every later pick seemingly unanswered; a paused failing load skipped on paused, so a pause didn't end a run of failures; play on a stopped device (shown paused) did nothing [HW 2026-10-28: each pick, play and next now one load and paused, re-picks answered] | `connect/src/spirc.rs` |

## Our changes to shairplay-rust
Meant to go upstream where they make the library more modular; each keeps the default behaviour (the test suite
passes with every feature and with ours, `ap2-core,ptp-timestamps`). Below the features, the fixes of a review of
the whole crate and its restructuring, which change the API: `AudioSession::audio`, one
`Decoder` trait for every stream (`RaopServerBuilder::decoders`), `PairingStore::put(id, key, admin)`, settings from
the builder.
