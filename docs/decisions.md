# Decisions

Why the project is built the way it is. The facts behind each are in the topic docs.

| Decision | Why |
|---|---|
| Our MCU firmware on Atmel's ASF, not hand-rolled drivers | the hand-rolled USB stack never enumerated; ASF's did at once. A hand-written `delay_ms()` once read the wrong system register and hung the CPU |
| Our MCU firmware at 48 MHz (stock: 66 MHz) | one PLL for the CPU and USB; everything timing-related was re-checked against stock |
| Our MCU firmware links at 0x80004000 and never touches the bootloader, the ISP word or the fuses | the B&W DFU bootloader stays the way back from any MCU build |
| The host talks to our MCU firmware in typed messages over control transfers to a vendor interface (EP0), defined in `protocol/host/src/lib.rs` | the text console's output had to be scraped with sleeps and regexes by every tool; a second CDC port for the module console needs three endpoints and the USBB has one left (control, audio, HID and the CDC take six of seven), EP0 needs none (the one left is the bulk pipe that carries updates); USB checks and retries each transfer, so a message needs no framing; the emulator's USB bridge (the DFU tool's) carries it unchanged. The C and the tools' Python are generated from the spec, like the SPI protocol's |
| The host link is the only way to drive our MCU firmware: typed requests with typed replies, no command-line console | a text console behind a request was a second, untyped protocol: every module carried a parser, tools scraped its output, and bring-up commands (raw amp control around the interlock, test tones, a fake USB host) lingered. What stays is what the speaker needs and what diagnosis reads (`Diag`); one-off probing goes through `Peek`/`Poke` |
| The host link only grows: fields appended, ids never reused, decoders tolerant of shorter and longer messages; `spec.lock` enforces it | a hosted page or an old tool meets firmware of any age; exact version matching would make every change break someone |
| Requests that change the speaker need a press of ON/OFF on it (the gate), unless its owner opened the gate for good; a firmware's first start after a flash is unlocked for 10 minutes | USB access is no longer physical presence once a browser can reach the port (WebUSB): any page the user lets at it could flash, enable the debug shell or change the Wi-Fi. A press is the one thing a page can't do; a lab unit opens the gate once, at the speaker. The first start of a just-flashed firmware gives nothing away: getting it flashed took a press or the key-hold into DFU, where anything can be written; and an install that needs a press half-way stops when the person has stepped away |
| The host tools claim the vendor interface | one program at a time: two clients would take each other's replies and split the log |
| The module's console goes over the host link (`Console`, `ConsoleWrite`, POLL's CONSOLE records), not a CDC port | one transport for every tool and the web page (WebUSB reaches the vendor interface; a page can't use a serial port it wasn't granted, and Firefox and Safari have no Web Serial); the CDC port's three endpoints went to USB audio's status interrupt and the pipe's second bank; the console's open is gated like every request that changes the speaker |
| Builds identify themselves by commit and date, stamped after the build (MCU) or written into `/etc/os-release` (module OS) | a unit's two boards can be told apart from any other build; the MCU's stamp is patched into the linked image on the host, so a commit doesn't rebuild it on the Linux builder |
| Module OS = the Nokia HD-1 Linux kernel (unmodified binary) with our own userspace | its drivers cover Ethernet, Wi-Fi, audio and NAND for this chip family, and Linux brings the streaming userland. Our bare-metal Rust OS was dropped; its link code lives on in `module/link` |
| Userspace: musl, static busybox, Rust apps | glibc refuses a 2.6.24 kernel; musl falls back to the old syscalls. Two Rust busybox replacements were tried and dropped (`module/os/README.md`) |
| Keep the stock preloader and BL2 in every module image | a corrupt image falls back to BL2 by itself; BL2 is the module's recovery path |
| Install everything over USB: the system with `zd1 update`, the `.bcd` (stub, kernel, rescue) with the MCU bootloader's relay or `zd1 xmodem`; BL2's web updater only as a fallback | (`docs/module/updater.md`): a speaker has no Ethernet cable to count on, USB reaches both boards, and the relay works from any state of the module (an invalid app partition too) |
| Reach BL2 with `Module ESC` (BL1's serial menu over the module console, driven by the MCU) | works whatever the image does, as long as BL1 runs; HCR 0x21 needs a running image that answers it. The MCU releases the reset, so it alone knows when BL1's 2 s window opens: from the host over the host link the 0x02 came too late [EMU]; it sends nothing blind (the menu has "6) Erase Flash"), and what BL1 prints is in the log or the console |
| No escape window in our boot stub | `zd1 module esc` covers a broken image and `zd1-linkd` answers HCR 0x21 once Linux is up; a window cost seconds of every boot |
| The boot stub reports 0x2000 (booting), `zd1-linkd` 0x2100 | the stock MCU starts its setup task once on 0x2100; a module that then goes silent (stub to kernel) leaves the stock MCU stuck. 0x2000 is the stock status for "not usable yet" |
| Our OS reads PersParam raw, read-only | the kernel's soft ECC miscorrects normal MTD reads; writing the store stays BL2's and the stock app's job |
| The NAND in `mtdparts` partitions: the vendor area read-only, our two system slots and the data partition JFFS2 | the initramfs is RAM for good (9.2 MB of 31); the kernel has JFFS2 and the Nokia HD-1 ran its rootfs on it with this NAND driver; pages Linux writes carry Linux's ECC and read back right (only the vendor's are miscorrected); the read-only vendor partition keeps the kernel from ever writing BL1, BL2 or PersParam |
| The system lives in two slots, each a whole root (busybox, zd1, /etc, the init scripts) the kernel mounts directly; the app partition holds the boot stub, the kernel and a rescue initramfs | everything that changes is written by our OS through MTD, never by BL2 or the relay (6 min, erases the app partition first); the running slot is never written, a new one is started once on trial; no file system in RAM, no second busybox in the way of every boot |
| The MCU chooses the slot (EEPROM: the good one, one to try once) and tells the boot stub at every boot (SPI reg 0xC4) | the MCU already waits for the module's ready and is the one that can power-cycle it: the trial, its confirmation (ready) and the fall-back (no ready, or a restart before it) are one state machine in one place; the stub needs no NAND or JFFS2 code; the host commits an update with one request (`Boot`) |
| Nokia's kernel stored deflated in the payload, inflated by our boot stub (miniz_oxide, `no_std`) | the kernel stays the unmodified binary; the `.bcd` halves (3.8 → 2 MB: the relay a minute shorter, the preloader reads 1.5 MB less); the inflate takes 0.7 s on the unit, the D-cache on through a flat MMU map (2.5 s without) |
| The `.bcd` carries no system: the stub, the kernel and the rescue; the system goes into a slot over USB (`zd1 update`), the first one too | the relay writes 2 MB instead of 8.8 (85 s instead of ~6 min) and the system isn't limited by the app partition's 10 MB; one way into a slot instead of two |
| The update's data goes over the module console's UART at 1 Mbaud, in CRC'd frames, four in flight, answered by the module | the SPI link moves ~10 KB/s; the UART runs at 1 Mbaud on both ends; J2 has no RTS/CTS and Linux's tty buffer is 4 KB, so the module paces the MCU (go-back-N on a bad or missing frame), and the USB side waits in the pipe (NAKs) |
| Two busybox builds from one applet list each (`os.toml`), everything else off | the rescue's is 0.2 MB gzip, the system's 0.44 (defconfig's: 0.8); no servers on the speaker but the debug shell's telnetd |
| Settings live on the data partition, set over USB through the MCU (or a shell on the module); nothing on the network changes them until a module API with its own authentication exists | nothing on the network can rename the speaker or point it at another network; the Wi-Fi passphrase never leaves the computer (the key is derived there). A small API on the module for home automation is planned (`docs/backlog.md`): it will serve the State record as JSON and take settings with a credential of its own |
| The module OS's debug services are switched by the MCU, off in the normal image | a root shell and raw memory on the network would make the speaker anybody's; the MCU is reachable only over the speaker's USB port, and keeps the choice in RAM |
| Wi-Fi MAC = MAC0 with the locally administered bit, eth0 = MAC0 | stock used MAC0 for both, one interface at a time; with both up a shared MAC confuses switches, DHCP, ARP and mDNS, and MAC0 + 1 may be another unit's |
| Receivers: our `zd1-snapcast` (Rust), `zd1-airplay` on shairplay-rust, `zd1-spotify` on librespot | zd1-snapcast: small, no C dependencies, sync tuned to this driver; shairplay-rust: AirPlay 1 and 2 in pure Rust (FairPlay, pairing, PTP, mDNS) instead of shairport-sync's C stack (OpenSSL, Avahi, FFmpeg, nqptp). librespot: the only Spotify Connect implementation outside Spotify's own. The libraries forked and changed for this CPU and kernel (`module/os/forks.md`), the changes meant for upstream. Every receiver talks to the speaker only through `zd1-linkd`, which also decides who has it (the newest `playing` source) |
| The audio path is integer end to end | no FPU: float decoders and resamplers need 1-13x real time here (`docs/streaming.md`); our fixed-point decoders, ALAC, and integer samples to ALSA (AirPlay at the stream's own rate, Snapcast through its integer resampler to 44.1 kHz) |
| Our Rust programs as one executable (`apps/zd1`, busybox style) | every static program carried its own std (and alsa-lib): one copy saves 3.4 MB, of the system slot and of the rescue, which lives in RAM |
| std built from source for the module's programs (`-Zbuild-std`, the boot stub's nightly), with our size profile and without its backtrace feature | the core build went from 594 to 318 KB: std compiled for size and LTO'd with our code, and no symbolizer (gimli, addr2line, rustc-demangle: 82 KB) that could never name anything in a stripped binary aborting on panic; panic messages stay |
| The speaker's keys and knob go to the source, as with the stock module | Snapcast: JSON-RPC `Stream.Control`; AirPlay: the library's remote control (DACP / AirPlay 2). Play/pause mutes locally when a Snapcast stream can't be controlled |
| Warp0 for whole packets and frames (decrypt + ALAC decode for realtime AirPlay, AAC, Vorbis, FLAC), results collected in order later (the ARM never waits; HZ = 100 sleeps would cost 10 ms); its firmware in its local RAM; the ARM hands data over by `memcpy` through the uncached window | burst copies cost the ARM ~0.03 us/byte in and out, a few % of a cipher (word-at-a-time copies were 10x slower); a cached hand-off needs ~20 us syscalls per buffer; in local RAM Warp0 runs at one cycle per instruction and load, from SDRAM its data costs ~19 cycles (`module/warp0/README.md`) |
| One protocol spec (`protocol/`) for both sides of the MCU link | the MCU's C is generated from the Rust spec, so the two sides can't drift |
| Emulator on Renode | the QEMU pair (two processes, host-time sync) was slow and flaky; Renode gives one virtual clock and deterministic linked runs |
| The emulator is a development and RE aid, with no regression suite | the models were written from the vendor firmware, so scenarios checking modelled vendor behaviour proved little about the unit and cost upkeep; `zemu run` boots our OS, runs commands, traces the drivers. |
| Emulator state = the factory images of a dummy-MAC unit | no per-unit data (and no Wi-Fi settings) in the test images |
| Emulated Warp timing leaves out contention from the ARM and DMA | it depends on the ARM's memory traffic (Warp0 SDRAM loads 18 cycles idle, 33 with the ARM writing 57 MB/s), and Renode's ARM has no memory timing to derive it from; a guessed load factor would make emulated Warp timing look more precise than it is. The Warp-on-Warp part, measured and derivable, is modelled |
| The emulator develops and rehearses; the unit proves | emulator passes have repeatedly differed from the unit (pads, PHY, GPIO polarity, ECC, BL1); recovery costs minutes (`zd1 module esc`, JTAG, DFU backups) |
| Our own fixed-point decoders (`module/codecs`: AAC-LC, Vorbis, FLAC) | no FPU here; FDK's licence is not GPL-compatible and it is 800 KB of the receiver; ours are small integer C that also runs on Warp0: AAC within 1-4 LSB of FDK and faster on the ARM926 (14.8 % vs 18.5 %), Vorbis within 1-3 LSB of libvorbis (20.4 % vs Tremor's 23.7 %), FLAC bit-exact (the Snapcast client 15.2 % vs 17 % with claxon) |
| Our MCU firmware drives our module OS only; the stock module app is a detected state (STOCK), not a dialect; who wants stock rolls both boards back | the stock dialect (DRC queue, XML play state, attenuation volume) existed for a pairing nobody runs; what recovery needs is the stock framing and a handful of registers, which stay as the base layer (`docs/web.md`, Pairings) |
| A frozen base layer on the module link (status, version, link protocol, hello, boot choice, update, shutdown, HCR) that every version of ours speaks for good; features above it versioned by reg 0xD5; a mismatch is a reported state | any pairing of our own versions, MCU and OS, the rescue included, can boot, say what it is and update; the order of the two boards' updates stops mattering, a slot rolled back still updates |
| Install and rollback are single flows in `host/core`, module first both ways; a release is a pair (MCU firmware, system image, `.bcd`) in one manifest the page reads from its own origin | the relay needs nothing from the MCU app, and our firmware over the stock module is the state we least want; commit versions don't order, a list does; same origin needs no API, CORS or rate limit (`docs/web.md`) |
| The module's state is one typed record in the protocol spec, `State`: the settings are its writable fields (type, maximum, format, default declared once), the status the rest; pushed to the MCU, read whole by the host; other records (lists) the same way | two schemas had grown for one thing (a type table in the settings crate, strings on the host, and a text document about to be parsed by the page); the typed host link exists because untyped text gets scraped and drifts. One declaration gives the module its validation, the host its types, the page its form and a future module API its JSON; the MCU stays a byte relay |
| Each interface has the same address settings (off, DHCP, static with gateway and DNS); Wi-Fi adds the network | the wired port was DHCP-only because it had only been the lab link; one model for both is what a person expects and what the page can render from the spec |
